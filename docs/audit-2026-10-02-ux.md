# UX/UI Audit — 2026-10-02 (images, loading, feedback)

Branch: `ux-redesign-images-loading`. Scope: the Customer site, Seller panel and Admin panel, with most attention on **image upload**, **image viewing** and **loading screens**. Most CakeHub users are not technical, so each finding was judged by one question: *would someone who isn't comfortable with computers know what is happening and what to do next?*

Frontend only. No backend, schema, route or dependency changes.

## 1. Findings and fixes

### Loading

| # | Problem | Where | Fix |
|---|---|---|---|
| L1 | Every Inertia page change, even a 100 ms one, put up a full-screen blurred "Loading CakeHub" overlay. Fast clicks made the screen flash, and the page underneath was blocked. | `LoadingScreen.tsx` (global) | Removed the blocking overlay. Page changes now show Inertia's built-in thin top progress bar in brand pink, with a 200 ms delay so fast visits don't flicker. A small non-blocking "Loading, please wait…" pill appears only after 1.2 s, changes to a "taking longer than usual" message after 8 s, and a clear "You seem to be offline" message appears on network errors. |
| L2 | All 34 pages were bundled into one 1.36 MB script, so first load on mobile data was slow. Nothing was shown during that time: a blank white screen. | `app.tsx`, `app.blade.php` | Pages are now code-split: the entry script is about 36 KB plus the current page's chunk. Added a lightweight CSS-only first-load splash in the root template, removed once the app starts. |
| L3 | Photos appeared suddenly and pushed content around. A slow or broken photo showed the browser's broken-image icon. | All customer cards, storefront, ads | New `SmartImage`: reserves the image's space, shows a shimmer while loading, fades the photo in, and shows a friendly "No photo yet" tile if the photo is missing or fails. |
| L4 | The "Near me" search showed a single line of text while it waited. Non-OK API responses were treated as "no bakers found". | Customer Home | Skeleton cards while searching. Failed requests now show the location/error message instead of a misleading empty result. |
| L5 | The bank-account list on the payment step said "Loading bank accounts…" forever if the request failed. | `PaymentSlipForm` | Skeleton while loading, plus an error state with a "Try again" button. |

### Image upload

| # | Problem | Where | Fix |
|---|---|---|---|
| U1 | Product photos could only be added after the product had been saved once. The "Add product" page had no photo section, and nothing told sellers to come back. | Seller › Listings › Add product | Photos can be picked while creating a product. They are previewed straight away and uploaded right after the product is saved, with "Uploading photo 2 of 3…" shown. If any photo fails, the seller lands on the edit page with a banner asking them to add it again. |
| U2 | Photos had to be uploaded one at a time with a raw browser file input ("Choose file / No file chosen"). There was no drag-and-drop and no progress, only a spinner with "Uploading image to cloud…". | Listing form, Store profile, payment slips, payouts, documents | New `FileDropzone`: a large tap/drag target ("Tap to choose a photo" on phones) that shows allowed types and size limit up front. It accepts several photos at once where it makes sense. Uploads show a real percentage progress bar (`api.upload` now reports progress). |
| U3 | A wrong file type or an oversized file was only rejected after the upload finished, with a technical message. | Most upload points | Checks happen in the browser before anything is sent, using the same rules as the backend FormRequests. | U4 | Admin category/ad images were changed by clicking a 40 px thumbnail covered by an invisible file input. | U5 | Logo and cover upload was a raw file input under a small preview. | U6 | Payment and payout slips gave no confirmation of which file was picked. | Payment step, Admin › Seller payouts | New `SelectedFile` chip: thumbnail (or PDF icon), file name, size, and a "Change" button, so a wrong screenshot is caught before it is sent. |

| U8 | The Remove button on a product photo was a tiny text link, and removing a photo failed silently. | Listing form | 40 px trash button with a confirmation dialog ("Keep photo" / "Remove photo") and an error message if removal fails. |

|---|---|---|---|

|---|---|---|---|

## 2. New shared building blocks

All live in `resources/js/components/shared/` unless noted. Use these rather than raw `<img>` / `<input type="file">` in new screens.

- `SmartImage`: every remote photo.
- `ProductGallery` + `ImageLightbox`: multi-photo viewing and full-screen view.
- `FileDropzone`: every file picker. Pass a rule from `lib/files.ts` (`IMAGE_RULE`, `SLIP_RULE`, `DOCUMENT_RULE`, which mirror the backend `mimes`/`max` rules).
- `ImageUploadField`: single saved image (logo, cover).
- `ImageThumbUpload`: image in a dense list row.
- `ProductPhotoManager`: the listing photo grid.
- `SelectedFile`: confirms a picked file before sending.
- `ProgressBar`, `SlipPreviewDialog`, `Toaster`.
- `lib/toast.ts`: `toast.success()` / `toast.error()`.
- `lib/errors.ts`: `errorMessage(err, field?, fallback?)` gets the most useful message from a rejected `api` call.
- `lib/statusTone.ts`: the traffic-light badge helper the design doc already called for but which didn't exist yet. It is applied to documents and payouts so far.
- `api.upload(path, formData, { onProgress })`: now uses XHR so upload progress can be reported.

## 3. Not done: needs a decision (per CLAUDE.md Rule 2)

1. **Reorder photos / choose the main photo.** The first uploaded photo is always the main one, and there is no reorder endpoint. Adding one is a backend and feature change.
2. **Server-side thumbnails.** Cards download full-size Cloudinary images. Requesting smaller Cloudinary transformations (for example, a width limit on card images) would make browsing much faster on mobile, but it changes how image URLs are built on the backend.
3. **Toast library.** I built a ~60-line notifier instead of adding shadcn's recommended `sonner`, to avoid a new dependency. Switching is easy if `sonner` is preferred.
4. **Status badges elsewhere.** Order, subscription, payment and seller-status badges still use the old default/secondary variants. They should move to `statusTone` for consistency.
5. **Live browser pass.** The required chrome-ui-testing pass at 375/768/1280 px has **not** been run. No browser tool was available in this session, and the local `.env` points at the hosted Supabase database, so uploads were not exercised end to end. Unit tests and the production build pass.
